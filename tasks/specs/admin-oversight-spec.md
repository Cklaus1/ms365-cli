## Summary

Two read-only, admin-facing features:
1. **`ms365 reports …`**: Microsoft's aggregate usage reports. Tenant-level daily counts (email, Teams, active users) and a department roll-up. Counts only: **no message content, no per-person rows, and no department group smaller than 5 people.**
2. **`ms365 audit-trail`**: oversight of access itself. Who accessed which mailbox and how (owner, delegate, admin, app), which apps hold broad mail access, and which admin roles or consents changed. It reads Microsoft's audit log and directory, so it shows *access events and grants*, never the content that was accessed. (`audit-trail mailbox` creates a saved query with a POST; see AO-14/AO-25.)

Worked example that motivated AO-28..AO-32 (2026-10-17, done by hand from a Purview CSV export): a user read three delegated mailboxes (one of them a disabled admin account's) through a third-party connector that had tenant-wide delegated consent including `Mail.Read.Shared`. The commands in this spec answer exactly those questions without a manual export.

## Design rules

- **No collection of content.** ms365 gets no command that reads other people's mail, chats or calendars. Reports are Microsoft-computed counts; audit-trail prints an allow-list of access metadata (AO-9).
- **Small groups are never shown.** Department roll-ups pool groups under the minimum into one "Other" row and drop even that pool if it is under the minimum, so no row describes fewer than 5 people. The floor is not configurable below 5. Groups hidden at the floor stay hidden at every higher `--min-group-size` (AO-22).
- **Least privilege.** Per-workload audit scopes where Graph offers them (`AuditLogsQuery-Exchange.Read.All`, not `AuditLogsQuery.Read.All`).
- **Admins only, enforced by Microsoft.** Graph refuses callers without the reports/audit roles; the CLI maps those refusals to clear hints and adds no bypass.
