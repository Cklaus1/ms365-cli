## Summary

ms365 already caches several accounts and has named profiles (`--profile`, `--account`), but credentials sit in one plaintext 0600 file and every profile is the same kind. This spec:
- **Credential storage.** Moves the refresh-token cache into the OS keychain where one works, with a silent fallback to the 0600 file, so sign-in stays one-time.
- **Two profile types.** `user` (default, today's behaviour) and `admin` (token borrowed from the Azure CLI on demand, never stored by ms365).

Every identity remains the signed-in person acting for themselves. No friction is added: after one sign-in, commands stay silent until Microsoft itself requires re-authentication.

**Threat model (one paragraph).** [ADDED: review item 4] The keychain protects credentials *at rest*: backups, Time Machine/snapshots, synced or copied home directories, a stolen disk, a locked keychain when the user is logged out, and the "cat ~/.config/ms365-cli/token-cache.json" class of accident. It does **not** protect against code running as the same OS user: on every platform the same user can run `security find-generic-password -w`, `secret-tool lookup` or DPAPI `Unprotect` and read the items without a prompt (macOS: items created by `/usr/bin/security` carry it in their access list, so reads through `security` never prompt†). ID-1's wording and the README must say this plainly; same-user malware is out of scope here as it is for every CLI that keeps a session.

[REVISED: the secret must never appear in argv — `ps` shows it to every user] <br>• **macOS:** write with `security -i` (interactive mode reads commands from stdin — verified in security(1)): stdin = `add-generic-password -U -a <acct> -s <svc> -w <base64 secret>\n`; argv holds only `-i`. The value is base64 so it needs no quoting and `find-generic-password -s <svc> -a <acct> -w` returns it as one printable line†. Read: `find-generic-password … -w`; delete: `delete-generic-password -s <svc> -a <acct>`. `-w` with no value prompts on the TTY, not stdin — unusable non-interactively†. <br>• **Linux:** `secret-tool store --label=<label> service <svc> account <acct>` reads the secret from stdin until EOF (verified in secret-tool(1)); `secret-tool lookup service <svc> account <acct>`; `secret-tool clear …`; `secret-tool search --all service <svc>` for `list()`. Only when `DBUS_SESSION_BUS_ADDRESS` is set *and* `secret-tool` is on PATH. <br>• **Windows:** DPAPI via PowerShell `[Security.Cryptography.ProtectedData]::Protect/Unprotect(bytes, $null, 'CurrentUser')` (verified: CurrentUser scope = decryptable only by the same Windows user; Windows-only). The script is passed with `-EncodedCommand` (no secret in it) and reads the plaintext from stdin, writing the base64 blob to stdout; blobs live in `configDir()/credentials/<acct>.dpapi`. `ConvertFrom-SecureString` without `-Key` is also DPAPI but round-trips through UTF-16 SecureString; `cmdkey` is dropped (password on argv, 2560-byte blob limit, no read-back). Needs `Add-Type -AssemblyName System.Security` on Windows PowerShell 5.1†. <br>• **Service name:** `ms365-cli:<first 8 hex of sha256(configDir())>` so two config directories (tests, `MS365_CLI_CONFIG_DIR`) never share items; account attribute = `homeAccountId`. |
| ID-4 | P2 | The storage choice must be silent and predictable. | Friction comes from prompts and surprise failures; a store that flips between runs makes accounts appear and vanish (split-brain). | [REVISED: config-dir level, sticky] Setting `storage: auto \| keychain \| file` lives in `configDir()/storage.json` (not per profile — profiles share one cache; see Current state), set by `auth storage use` or `MS365_CLI_STORAGE` (env wins, for CI and tests). `auto` resolves **once**, on the first write (login or migration), with a probe of ≤1.5 s (write-read-delete of a probe item); the result (`resolved: keychain\|file`, `probedAt`, `reason`) is recorded in `storage.json` and reused until `auth storage use auto` or `auth login` re-probes. On fallback it prints one stderr line the first time ("keychain unavailable (<reason>); using the 0600 file — `ms365 auth storage show`"), recorded as `noticeShown` in the same file. Under `keychain`, a failure is exit 3 `keychain_unavailable` with a fix (`ms365 auth storage use file`, or on macOS `security unlock-keychain`†). |
| ID-5 | P3 | Moving an existing file cache into the keychain needs a migration. | Avoid a re-login when someone switches to keychain storage. | The first successful keychain write imports `token-cache.json`'s credential sections, then rewrites the file without them (ID-6). `ms365 auth storage [show\|use keychain\|use file\|use auto]` switches explicitly and migrates in both directions; `use` holds the file lock for the whole migration and verifies by reading every item back before deleting the source. |
| ID-6 | P3 | Keychain item size limits. | One MSAL cache holding many accounts can exceed some backends' limits (Windows Credential Manager blobs are about 2.5 KB — the reason `cmdkey` is out) and one shared item makes every writer clobber every account. | [REVISED: concrete split, proven lossless by the cache shape above] One item per account, value = `{IdToken, AccessToken, RefreshToken}` entries whose `home_account_id` equals that account (base64 JSON, ~5–8 KB per account). `token-cache.json` keeps `Account` and `AppMetadata` (no secrets; `Account` doubles as the index — `auth accounts` and `list()` agree on it). `beforeCacheAccess` reassembles the full `{Account, IdToken, AccessToken, RefreshToken, AppMetadata}` object and calls `deserialize()` once; `afterCacheAccess` (only when `cacheHasChanged`) serializes, splits by `home_account_id`, writes **only the accounts whose JSON changed**, deletes items for accounts no longer present, and read-modify-writes the file's `Account`/`AppMetadata` under `withFileLock`. Two processes refreshing different accounts therefore touch different items; today's last-writer-wins race on the shared file is reduced to the rare login-time `Account` write. Access tokens stay in the item (dropping them would force a network refresh on every command). |
| ID-7 | P2 | Profiles have no identity type. | `user` and `admin` need different sign-in and storage rules. | Add `type: 'user' \| 'admin'` (default `user`) to `Profile`, validated on load. [REVISED] `admin` requires `tenantId` (a real tenant, not `common`/`organizations`, because `az --tenant` needs one) and rejects `account` and `scopes` (`invalid_profile`); `clientId`/`orgMode` are ignored with a warning in `auth profile show`. `auth profile set <name> --type admin --tenant <t>`. |
| ID-8 | P2 | Admin identities shouldn't be stored at all. | An admin refresh token at rest is the highest-value thing on the machine. | `type: admin` profiles never write tokens: `AuthManager` gets a token source (`msal` \| `az`); for `az`, `getToken()` calls `azGraphToken(tenantId)` (existing, 60 s timeout) and caches the result in memory until `exp − 5 min`; long-running processes re-call az when it expires (az refreshes itself). Without az → exit 3 `az_required` with `az login --tenant <t>`; az not logged in → exit 3 with the same fix. [REVISED: which identity and scopes] The identity is **az's signed-in user through the Azure CLI first-party app**, so the token's `scp` is whatever that app has consented in the tenant (typically `Directory.AccessAsUser.All Group.ReadWrite.All User.ReadWrite.All AuditLog.Read.All …`†; `AuditLogsQuery.Read.All`, `Mail.*`, `Calendars.*`, `Reports.Read.All` are not in it). Pre-flight runs unchanged against that `scp` (`grantedScopes()` decodes the az token — it is a JWT), so an admin profile can only run commands whose catalog scopes it covers (`groups`, `user`, `resolve`, `grant-scopes`); anything else exits 4 `missing_scope` with a profile-aware message: `"<cmd>" needs <scope>; the Azure CLI token used by admin profile "<name>" does not include it — use a user profile (ms365 --org-mode auth login) for this command`. `auth login`/`logout`/`accounts`/`select`/`remove` under an admin profile exit 2 `usage` ("admin profiles sign in with az login"); `auth status`/`scopes` report the az identity and its `scp`. ## Acceptance criteria

1. On macOS or Windows with `storage: keychain`, after `ms365 auth login`, `token-cache.json` contains no `IdToken`/`AccessToken`/`RefreshToken` section (grep for `"secret"` finds nothing), and 50 consecutive commands produce no keychain prompt and no extra stderr. (real macOS + Windows)
2. On WSL or headless Linux with no D-Bus session, commands behave exactly as today (file storage), print the fallback notice once per config directory, and add no more than 1.5 s to the first write and 0 ms to later commands.
3. A keychain backend that hangs (stub tool that sleeps) never delays exit beyond its timeout (spawned test); the stub's argv never contains the secret.
4. `ms365 auth storage use keychain` then `use file` round-trips every cached account with no re-login: `JSON.parse` of the file before and after is deep-equal (key order is not promised), and `getAllAccounts()` lists the same `homeAccountId`s. [REVISED from "byte-identical"]
5. A `type: admin` profile writes nothing to any store (the store's `set` is never called, `token-cache.json` unchanged); without `az` it exits 3 with the `az login --tenant` hint; a command outside az's `scp` exits 4 with the profile-aware message; `auth login` under it exits 2.
6. Full suite, typecheck, `docs:check` and smoke stay green; no test reaches a real keychain (`MS365_CLI_STORAGE=file` in setup).
7. [ADDED] Windows: median wall time of `ms365 auth status` with `keychain` minus with `file` over 20 runs is reported, and OQ-3 is decided from it. (real Windows)
8. [ADDED] `ms365 auth logout` with `keychain` leaves no item for the service (`security find-generic-password` exit 44 / `secret-tool search` empty / `credentials/` gone).
9. [ADDED] Two processes refreshing two different accounts concurrently (spawned, like `test/fixtures/cache-writer.ts`) leave both accounts' items intact and the file's `Account` section with both entries.

## Review notes (Step 1)

- **Mechanism corrections.** macOS: `-w <value>` on argv is visible in `ps`; use `security -i` with the command on stdin (security(1) confirms `-i` reads commands from stdin; `-w` without a value prompts on the TTY). Linux: `secret-tool store` reads stdin until EOF (secret-tool(1)). Windows: `ProtectedData.Protect(…, CurrentUser)` is Windows-only and per-user (MS docs); `ConvertFrom-SecureString` without `-Key` is also DPAPI; neither needs the secret on argv when the plaintext goes through stdin. `cmdkey` dropped.
- **MSAL split proof.** All of `Account`, `IdToken`, `AccessToken`, `RefreshToken` entries carry `home_account_id`; `AppMetadata` carries none and is per client. Partitioning by `home_account_id` and reassembling is therefore lossless; `deserialize()` replaces the whole in-memory cache, so reassembly must finish before the single `deserialize()` call. Key order is not promised, hence AC 4's deep-equal.
- **Honest threat model.** The keychain does not isolate same-user processes on any platform; ID-1 and the README now say so. This also means ID-12's "Always Allow" scenario does not exist with the `security` tool as accessor.
- **Sequencing.** IDT-4 (admin) and IDT-1 (seam) are independent and fully testable on this WSL box; IDT-2/3 are testable only with stub tools here. Ship with OQ-1 = (b); IDT-7 on real hardware decides the default.
- **Needs a real macOS machine (†):** `security -i` quoting and base64 round-trip; no-prompt reads via `security` on a locked/unlocked login keychain and over SSH; exit code 44 for a missing item; item size with ~8 KB values. **Needs a real Windows machine (†):** `Add-Type System.Security` on PowerShell 5.1 vs `pwsh`; `-EncodedCommand` + stdin plumbing from `spawnSync`; the AC 7 timing; UTF-8 vs UTF-16 stdin decoding. **Tenant-dependent (†):** az's Graph token `scp` set in ID-8.
