# DRAFT — Output routing and flag-grammar consistency

**Status:** DRAFT — must pass its own Step 1 adversarial review before any build. Not scheduled.

**As of:** 2026-10-14 · **Scope:** `src/**` at `ed5bcff` (branch `build/followup-specs`) · **Source:** `tasks/opportunities.md` lines 32, 33, 34 · **Theme priority:** P3 · **Builds on:** DECISIONS.md F1/F2 (dry-run trace on stderr, one trailer), VT9 (`test/lint-output.test.ts`), D27–D30 (no legacy consumers, so no compat shims)

## Summary

Three nits from the follow-up run share a root cause: there's no single rule for (a) how a non-data line reaches stderr, (b) how a time span is written on the command line, or (c) what the dry-run trailer counts. `drive upload` and the Graph retry notices bypass `info()`, so `--quiet` can't drop them. Some retries are announced and others are silent. Durations come in five grammars across eight options (ISO `PT30M`, `30m`/`1h30m`, bare seconds, bare minutes, bare ms). The digest trailer under-counts because some requests depend on data. Widening one level turned up the same split for booleans (`--enabled true|false` vs `--disabled`, `--font-bold [bool]`, env flags) and dates (`YYYY-MM-DD`-only vs natural `parseTime`, plus an unvalidated `--expiry`). This spec adds `warn()`, `parseDuration()` and `envFlag()` helpers, plus a "more depending on data" trailer form, and moves every caller onto them.

Method: every row was read against `ed5bcff`. **(ran)** = reproduced via `tsx src/index.ts --dry-run …`. † = depends on Graph behaviour not checked against a live tenant (D24/N3). None of the three source items has been fixed yet.

## Open questions

| # | Question | Options | Recommendation | Tag |
|---|---|---|---|---|
| Q1 | Which duration grammar should the CLI accept (OC-6, OC-7)? | (a) ISO 8601 only; (b) humane `1h30m` only; (c) both, plus a bare number in the option's documented unit | **(c)**. One `parseDuration(v, {unit, min, max}) → ms` accepting `^(\d+w)?(\d+d)?(\d+h)?(\d+m)?(\d+s)?$` (at least one part), ISO `P[nD]T[nH][nM][nS]` (any case), or a bare integer in `unit`. Reject fractions, zero and negatives. Out-of-range errors print in the option's unit (`--interval must be at least 15s`). `ms` is accepted only as a bare `--page-delay` number. Keeping bare numbers makes no default change; accepting ISO costs one extra regex. | engineering |
| Q2 ⚠ | Should `-q` drop warnings (OC-4)? | (a) yes: `-q` drops all non-error stderr, as now for `watch`; (b) no: `warn()` survives `-q`, which only drops progress/status (`info()`/`success()`) | **(b)**. These warnings say the output is incomplete or the baseline was reset. A script that passes `-q` to silence chatter still needs to know that. Retry notices (OC-2/3) are progress, so they use `info()`. Under MCP, `warn()` lines go to the MCP log like any other stderr. | engineering |
| Q3 | How should the trace and trailer show data-dependent requests (OC-8, OC-9)? | (a) a lower-bound count `N+ request(s)`; (b) `N request(s) previewed, more depending on data`, plus one `then … (not previewed)` trace line per deferred step; (c) synthesize fake list IDs and trace the loop | **(b)**. It's precise about what was traced, and the `then` line tells the agent the shape (up to 5, once per page). (c) invents data, which F6 rejects. `noteDeferred()` doesn't change `previewCount()`, so the snapshot count stays honest. The MCP dry-run result (XT7) carries the same text. | engineering |
| Q4 | What does the trailer count (OC-10)? | (a) logical operations (as now, but inconsistent); (b) HTTP requests the real run would send | **(b)**. "Requests" reads as HTTP, matching the audit log and throttling budgets. The per-item batch trace lines stay, for readability. | engineering |
| Q5 | `search --size/--from` → `--top/--skip` (OC-15)? | (a) rename; (b) keep Graph's names and add `--top` as an alias; (c) leave as is | **(a)**. D27: no legacy consumers. One vocabulary helps agents more than mirroring the Graph request body does. | engineering |
| Q6 | Booleans for value-carrying options (OC-11)? | (a) negatable flag pairs; (b) a strict `<bool>` parser (`true/false/yes/no/1/0`) | **(a)** for CLI flags (commander-native, boolean in the MCP schema, already used by `--no-notify`/`--no-org-mode`). The strict parser from (b) lives only in `envFlag()` (OC-12). | engineering |
