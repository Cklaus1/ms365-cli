# DRAFT — Upload, Session and Send Robustness

**Status:** DRAFT — Step 1 adversarial review done 2026-10-14 against `b8b58d9` (branch `build/followup-specs`); see `## Review notes (Step 1)`. Not scheduled.

**As of:** 2026-10-14 · **Scope:** `src/**` at `41c41f3` (branch `build/ms365-findings-spec`); line refs re-checked at `b8b58d9` · **Theme:** P3 opportunities from the last build run, plus related instances found nearby (`[ADDED]`). Format and severities follow `docs/ms365-findings-spec.md`. There are no legacy consumers (D27–D30), so no compat shims.

## Summary

Drive uploads go through one session uploader that retries and resumes (`GraphClient.uploadInSession`). Mail attachment uploads use a second, hand-rolled loop that has no retry, no resume, no timeout and no audit line. The idempotency ledger (D23) has two gaps. A crash leaves a `pending` claim that blocks the key for 24 h. A timeout whose outcome is unknown drops the claim, so the retry the key exists for sends the mail again. Smaller issues: `mail reply --html` is ignored, `shared-send` and the Teams sends have no `--idempotency-key`, one transient error ends `watch --follow`, and `audit.log` rotation can lose the rotated generation when several processes write at once.

## Open questions

- **OQ-1 (needs-human): recovering from a stale or unknown claim (R-6, R-7).**
  - (a) Shorter pending TTL with auto-release. Simple, but it brings back duplicates.
  - (b) Owner-pid check that auto-releases dead claims. A dead owner says nothing about whether the send took effect.
  - (c) Pid check + staleness that report `outcome_unknown`, with an explicit `ms365 idempotency release <key>`.
  - **Recommend (c).** Auto-release defeats D23. The cost is a one-line manual step, and only after a crash.
- **OQ-2 (engineering): how `--html` reaches a reply (R-2).**
  - (a) `message.body` on `/reply`. One call, but it loses the quoted thread †.
  - (b) createReply → patch the body → send. Three calls, keeps the thread.
  - **Recommend (b).** It reuses `sendViaDraft`.
- **OQ-3 (needs-human): extend D23 to Teams sends (R-5)?**
  - (a) Mail and events only, as today.
  - (b) Add the key to the 4 Teams send commands.
  - **Recommend (b).** The ledger and the agent retry pattern are the same.
- **OQ-4 (engineering): the shared uploader API (R-1).** Expose a public `client.uploadSession(...)`, or keep `uploadLargeAttachment` in mail calling an exported free function? **Recommend a public `GraphClient` method.** It keeps read-only, dry-run and audit handling in one place.
- **OQ-5 (engineering): body-size timeout (R-9).**
  - (a) Scale the timeout in `send()`.
  - (b) Pass `timeoutMs` at the 6 call sites.
  - **Recommend (a).** It also covers future large POSTs.
- **OQ-6 (engineering) `[ADDED]`: exit code for a SIGINT that cuts a pass short (R-12).**
  - (a) 130, the shell convention for death by SIGINT; D2's table gains a footnote.
  - (b) 1 with `code: 'interrupted'`, staying inside D2's 0–7.
  - **Recommend (a).** A shell already reports 130 when a process dies of SIGINT, so scripts expect it; (b) would make "interrupted" indistinguishable from a generic failure. SIGINT during the sleep stays exit 0 (cursor saved, nothing lost).

## Acceptance criteria

1. **R-1/R-14:**
   - A mocked Outlook session that returns 503 on chunk 2, then 200 with `nextExpectedRanges`, completes, and every byte is sent exactly once after the resume point.
   - A 201 with an empty body succeeds. A 200 with `nextExpectedRanges` continues; a `200 '{}'` advances one chunk (`mail-agent.test.ts:34` still sees exactly 2 PUTs for 3 MiB + 1 byte).
   - A chunk that stalls past the timeout aborts and retries. A resume GET that stalls aborts and falls back to the last ranges.
   - `audit.log` gets one PUT line for the attachment upload.
   - The drive upload tests in `test/upload.test.ts` and the dry-run snapshot still pass, unchanged.
2. **R-2/R-3:**
   - `mail reply --html` issues createReply → GET → PATCH (`contentType: 'HTML'`, user HTML before the quoted body) → send.
   - Without `--html`, it issues a single `/reply` with `comment`.
   - `forward --html` works the same way. `reply --html` and `reply` with the same key raise `idempotency_conflict`.
3. **R-4/R-5:** A second `shared-send` (and each Teams send) with the same key and request makes no Graph POST and prints the stored result. A different request with the same key fails with `idempotency_conflict`.
4. **R-6:**
   - A pending entry with a dead pid on the same host, or older than 1 h, makes `checkKey` throw `idempotency_outcome_unknown`. A live pid gives `idempotency_in_progress`.
   - `ms365 idempotency release k` removes the entry, and the next send proceeds. `ms365 --dry-run idempotency release k` leaves the ledger unchanged.
   - `idempotency list` prints the entries as JSON. `describe`, the catalog guards, completion and `docs:check` pass with the new command.
5. **R-7/R-15:**
   - A POST to `/me/sendMail` that times out, or fails with `ECONNRESET`, or gets a 503, leaves an `unknown` entry, and the retry with the same key does not POST. `--error-format json` shows `"maybeProcessed": true`.
   - A pre-send connection error, a 429 or a 400 still drops the claim.
6. **R-8:** A failed attachment upload in `sendViaDraft` triggers one DELETE of the draft. A failure at `/send` triggers no DELETE.
7. **R-9:** `send()` with a 4 MB body and no `timeoutMs` arms a timer of at least 150 s, checked with fake timers. An explicit `timeoutMs` is never overridden.
8. **R-10:**
   - With `--follow --max-passes 3`, a pass that throws 503 is logged and followed by another pass after a longer sleep.
   - `auth_required` exits 3 immediately.
   - 10 consecutive failures exit with the last error's code.
9. **R-12:** A first SIGINT during a pass stops after the current page, the cursor file is unchanged, and the exit code is the OQ-6 choice. A SIGINT during the sleep still exits 0 with the cursor saved.
10. **R-13:** Two rotations interleaved under the test harness never replace a `.1` that is over 5 MB with a smaller file. `test/audit.test.ts:144` still passes.
11. Full suite green. The `generate-skills`, `describe` and completion snapshots and the README generated region (`npm run docs`) are updated for the new options (`--html` on forward, `--idempotency-key` ×5, `--max-failures`) and the `idempotency` command.
